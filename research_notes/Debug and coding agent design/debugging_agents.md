## Q1. What is the canonical workflow for an effective debugging agent?

### Takeaway
The convergent 2026 architecture is a gated pipeline — **reproduce → validate the reproduction → localize (static + runtime evidence) → hypothesize → instrument/inspect at runtime → patch → verify against both the reproduction and the pre-existing suite** — with the distinguishing feature versus 2024-era agents being that patching is *gated* on a validated reproduction and on runtime facts rather than on static code reading alone.

### Cited Findings
- Role-decomposed pipelines are the dominant published pattern: a **Reproducer** creates a reproduction script matching the issue description, a **Tester** verifies it and returns exception stack traces/output, and a **Programmer** repairs — as implemented in ByteDance's MarsCode Agent — [MarsCode Agent: Powered by LLM for Automated Bug Fixing](https://dev.to/marscode/marscode-agent-powered-by-llm-for-automated-bug-fixing-2j7a); the same Reproducer role appears in SpecRover and in PatchPilot's "self-reflection-based PoC reproduction" that iteratively generates and refines reproduction scripts — [Dissecting the SWE-Bench Leaderboards (arXiv 2506.17208)](https://arxiv.org/pdf/2506.17208) **[via search summary]**
- The "gate on reproduction" rule is stated explicitly by a practitioner team reporting 83.4% on SWE-bench Verified: "Only once the reproduction passes validation does the system allow the agent to start modifying code, ensuring that any patch generated is grounded in verified runtime facts — not in noise, a broken script, or an incorrect trigger path," and they argue the validation stage raises overall pass rate despite being slow — [How We Hit 83.4% on SWE-bench Verified (Part 1): Getting Reproduction Right](https://dev.to/morethananai/how-we-hit-834-on-swe-bench-verified-part-1-getting-reproduction-right-5077)
- debug-gym formalizes the loop as: given a repository, the agent *iteratively* interacts with investigation tools (eval, view, pdb, rewrite/edit, listdir, grep, bash) and only "once gathered enough information" proposes a patch — [debug-gym, Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/debug-gym-an-environment-for-ai-coding-tools-to-learn-how-to-debug-code-like-programmers/); [microsoft/debug-gym](https://github.com/microsoft/debug-gym)
- For production/observability debugging the same shape appears as an explicit hypothesis loop: Datadog's Bits Investigation "formulates hypotheses about the root cause," then "validates or rejects hypotheses using data from targeted queries," then recursively generates deeper sub-hypotheses, exploring or pruning branches based on supporting evidence — [How we built an AI SRE agent that investigates like a team of engineers](https://www.datadoghq.com/blog/building-bits-ai-sre/)
- Sentry's Seer performs backwards causal tracing rather than forward summarization: it "traces backward through stack traces, breadcrumbs, spans, and logs until it finds the line that actually started the problem, not just the frame that blew up" — [How Sentry's Seer Works, From Root Cause to Autofix](https://theaiengineer.substack.com/p/how-sentry-built-seer) **[via search summary]**
- The 2026 dynamic-analysis systems replace ad-hoc instrumentation with a structured runtime artifact: the Agent-centric Debugging Interface (ADI) exposes a **Frame Lifetime Trace (FLT)** per function invocation — arguments, final return value, a complete ordered trace of executed statements with their state modifications, and identifiers linking caller and callees — plus high-level navigational commands over program dynamic state — [Empowering Autonomous Debugging Agents with Efficient Dynamic Analysis (arXiv 2604.24212 / PACMSE doi 10.1145/3797126)](https://doi.org/10.1145/3797126) **[via search summary]**

### Inferences
- The measured stage that most reliably adds value is **reproduction validation**, not clever localization: every system that reports large gains (PatchPilot, MarsCode, SWE-Doctor, the 83.4% practitioner report) gates patching behind an executable reproduction, whereas localization quality varies widely across systems with similar end scores.
- "Instrument" has bifurcated into two implementations — (a) drive a real debugger (debug-gym, Debug2Fix, MCP DAP servers) and (b) capture a structured whole-execution trace once and let the agent navigate it (ADI/FLT, DAIRA). The trace-navigation branch reports better cost efficiency, which suggests step-by-step debugger stepping burns tokens on low-information steps.
- Regression verification is nearly universal but weakly specified in papers; the strongest empirical pressure on it comes from the overfitting literature (Q6), not from the workflow papers themselves.

### Gaps
- No single 2026 ablation study was found that isolates the marginal contribution of *each* stage (reproduce vs localize vs instrument vs verify) within one agent on one benchmark; the evidence is assembled from separate systems.
- A 2026 paper titled "Debugging the Debuggers: Failure-Anchored Structured Recovery for Software Engineering Agents" (arXiv 2605.08717) surfaced in search and appears directly relevant to workflow recovery, but arxiv.org was blocked so its contents and numbers could not be verified.

## Q2. Research on fault localization with LLMs — SBFL, coverage, LLM-based, hybrid

### Takeaway
Pure SBFL is no longer competitive as a standalone method, but coverage/spectrum data survives as a *retrieval and pruning prior* inside LLM agents; the 2025–2026 state of the art is multi-agent, repository-scale LLM localization augmented with graph/RAG retrieval, external memory, and runtime pruning, reporting roughly 9–19% relative Top-1 gains over the 2024 AutoFL baseline on Defects4J.

### Cited Findings
- The standard taxonomy in 2025–2026 papers is four-way: **Spectrum-Based (SBFL)**, **Mutation-Based (MBFL)**, **Learning-Based (LBFL)** and **LLM-based** fault localization, with SBFL characterized as relying on statistical analysis of test coverage data and "often lack[ing] accuracy" — [Improving LLM-Based Fault Localization with External Memory and Project Context (arXiv 2506.03585)](https://arxiv.org/pdf/2506.03585) **[via search summary]**
- **LLM4FL** (multi-agent, repository-level, graph-based retrieval + iterative refinement) outperforms AutoFL by **18.55% in Top-1 accuracy** on Defects4J V2.0.0 (675 faults across 14 Java projects) — [LLM4FL, OpenReview z91EvZbSI1](https://openreview.net/forum?id=z91EvZbSI1) **[via search summary]**
- **FaR-Loc** (LLM Functionality Extraction → Semantic Dense Retrieval → LLM Re-ranking) outperforms **SoapFL by 14.6%** and **AutoFL by 9.1%** in Top-1 accuracy on Defects4J; the same work reports that structure-aware code embedding models such as **UniXcoder improve Top-1 by up to 49.0%** over weaker embeddings — [Enhancing LLM-based Fault Localization with a Functionality-Aware RAG Framework (arXiv 2509.20552)](https://arxiv.org/abs/2509.20552) **[via search summary]**
- **MemFL** (external memory + project context) reports roughly **12.7% higher Top-1 than AutoFL** using GPT-4o-mini, localizing **350 bugs at Top-1 vs AutoFL's 331** under re-evaluation — [arXiv 2506.03585](https://arxiv.org/pdf/2506.03585) **[via search summary]**
- **SoapFL** (standard-operating-procedure, method-level) achieves **Top-1 on 175 of 395 bugs** on Defects4J v1.2.0 — [SoapFL, Illinois Experts](https://experts.illinois.edu/en/publications/soapfl-a-standard-operating-procedure-for-llm-based-method-level-/) **[via search summary]**; code at [IntHelloWorld/SoapFL](https://github.com/IntHelloWorld/SoapFL)
- **Baseline instability warning:** SoapFL and AutoFL were both originally evaluated with `gpt-3.5-turbo-0613`, which is no longer available, so later studies re-run them on newer models (e.g. GPT-4o-mini) — cross-paper Top-1 comparisons are therefore not apples-to-apples — [arXiv 2506.03585](https://arxiv.org/html/2506.03585v1) **[via search summary]**
- **Conflicting AutoFL figures:** one source reports AutoFL "localized 149 faults across 353 cases in Defects4J," while the MemFL comparison reports AutoFL at 331 Top-1 bugs; these are evidently different Defects4J subsets/versions and model backends — [arXiv 2509.20552](https://arxiv.org/pdf/2509.20552) vs [arXiv 2506.03585](https://arxiv.org/pdf/2506.03585) **[both via search summary]**
- **Hybrid SBFL+LLM is an active 2026 line:** CNFL incorporates LLM-evaluated *code naturalness* into the SBFL pipeline, prioritizing statements that deviate from typical coding patterns, evaluated on Defects4J with 5 representative SBFL formulas × 5 LLMs — [Software Fault Localization Approach with Coverage Matrix Optimization Boosted by LLM-Based Code Naturalness, Applied Sciences (doi 10.3390/app16094416)](https://doi.org/10.3390/app16094416)
- **Runtime-aware pruning** is the 2026 scaling answer: SieveFL applies "hierarchical runtime-aware pruning for scalable LLM-based fault localization" — [SieveFL (arXiv 2605.13491)](https://arxiv.org/html/2605.13491v1) **[title/abstract via search only]**
- Historical anchors (mark as such): AgentFL scaled LLM-based FL to project-level context (2024) — [arXiv 2403.16362](https://arxiv.org/html/2403.16362v1); test-free fault localization with LLMs (ICSE 2024) — [doi 10.1145/3597503.3623342](https://dl.acm.org/doi/10.1145/3597503.3623342); explainable LLM-based FL evaluation (PACMSE 2024) — [doi 10.1145/3660771](https://dl.acm.org/doi/10.1145/3660771); attention probing for scalable fault localization (2025) — [arXiv 2502.13966](https://arxiv.org/html/2502.13966v2)
- Industrial deployment exists: Google reports LLM-based automated diagnosis of integration test failures — [arXiv 2604.12108](https://arxiv.org/pdf/2604.12108) **[title only; contents not retrievable]**

### Inferences
- The pattern across LLM4FL, FaR-Loc, MemFL and SieveFL is that the winning lever in 2026 is **context construction** (graph retrieval, dense semantic retrieval, external memory, runtime pruning), not the localization prompt or the ranking formula. Coverage/spectrum data is most useful as a cheap candidate filter feeding those retrievers.
- Reported gains are consistently expressed as *relative* improvements over AutoFL/SoapFL rather than absolute Top-1 rates, which makes the field's absolute progress hard to read and is a sign that absolute Top-1 on Defects4J has plateaued in the roughly 40–55% band (inferred from SoapFL's 175/395 ≈ 44% plus single-digit-to-19% relative gains, not directly stated by any source).
- Defects4J remains the benchmark of record for method-level FL, which means most FL numbers are Java-only and do not transfer directly to the Python-dominated SWE-bench agent literature.

### Gaps
- Absolute Top-1/Top-3/Top-5 percentages for LLM4FL, FaR-Loc, MemFL and SieveFL could not be retrieved (arxiv.org and openreview.net blocked); only relative deltas versus AutoFL/SoapFL are sourced here.
- No 2026 head-to-head study was found that measures how much *coverage data specifically* contributes inside an agentic debugger (i.e., an ablation of coverage-in/coverage-out on SWE-bench-style tasks).
- No source found quantifying FL accuracy for non-Java, non-Python ecosystems.

## Q3. Interactive/runtime debugging for agents — debug-gym, RepoDebug, MCP debuggers, DAP. Does it beat print debugging?

### Takeaway
Yes, with caveats: the best-measured results show real debugger access adding roughly **11–15 percentage points** on SWE-bench Lite (debug-gym) and **>20% relative** improvement on GitBug-Java/SWE-Bench-Live (Debug2Fix), and structured execution-trace access (ADI) taking a *basic* agent to 63.8% on SWE-bench Verified at $1.28/task — but naive debugger access alone is not enough, and the strongest results come from delegating debugging to a subagent or pre-digesting the trace rather than letting the main agent step interactively.

### Cited Findings
- **debug-gym** (Microsoft Research, arXiv 2503.21557, March 2025; **MIT license**) is a text-based environment giving agents `bash`, `view`, `eval`, `pdb`, `grep`, `listdir`, `edit`, `submit`, plus MCP tools for dynamic external-server integration; it ships benchmarks `aider`, `swebench` (with a `swebench-debug` variant), `swesmith`, `r2egym`, `mini_nightmare` (10 hand-crafted buggy snippets), Docker and Kubernetes terminal backends, and two agents — `froggy_agent` and an oracle `solution_agent` applying gold patches. Source layout: `debug_gym/gym` (environment + tools), `debug_gym/agents`, `debug_gym/llms`. A `FreeEnv` extension generalizes it beyond debugging — [microsoft/debug-gym](https://github.com/microsoft/debug-gym)
- **The headline debug-gym measurement:** on SWE-bench Lite (300 issues), Claude 3.7 Sonnet scored **37.2% in rewrite mode with no debugger, 48.4% with the debugger tool, and 52.1% with "debug(5)"** — where pdb is only unlocked after the 5th rewrite attempt — i.e. +11.2 pp for a debugger and +14.9 pp for delayed-debugger scaffolding — [debug-gym results](https://www.microsoft.com/en-us/research/blog/debug-gym-an-environment-for-ai-coding-tools-to-learn-how-to-debug-code-like-programmers/) **[exact figures via search summary of the same MSR blog / arXiv 2503.21557]**
- Microsoft's own caveat: nine LLM backbones were tested and "even with debugging tools, our simple prompt-based agent rarely solves more than half of the SWE-bench Lite issues" — [MSR debug-gym blog](https://www.microsoft.com/en-us/research/blog/debug-gym-an-environment-for-ai-coding-tools-to-learn-how-to-debug-code-like-programmers/)
- **Debug2Fix** (Spandan Garg, Yufan Huang; Microsoft Research; **February 2026**; arXiv 2602.18571) incorporates interactive debugging as a **subagent** with debuggers for both Java and Python, reporting **">20% improvement in performance compared to the baseline for certain models"** on **GitBug-Java** and **SWE-Bench-Live**, and — notably — that weaker models (GPT-5, Claude Haiku 4.5) **matched or exceeded** a stronger model (Claude Sonnet 4.5) when using the framework — [Debug2Fix, Microsoft Research](https://www.microsoft.com/en-us/research/publication/debug2fix-debug2fix-supercharging-coding-agents-with-interactive-debugging-capabilities/)
- **Direct print-vs-debugger comparison from Debug2Fix:** the baseline agent "engaged in repeated edit and bash calls to do print-debugging, but struggled to find where bugs were coming from due to how deep in the codebase the issue was," whereas Debug2Fix's Debug Subagent "set a breakpoint directly in the test script and inspected local variables while stepping through the code"; GPT-5 saw the largest gains with a **>98% Debug Subagent call rate** on GitBug-Java — [Debug2Fix (arXiv 2602.18571v2)](https://arxiv.org/html/2602.18571v2) **[via search summary]**
- **ADI / Frame Lifetime Trace**: equipping a *basic* agent with ADI resolves **63.8% of SWE-bench Verified**, slightly outperforming the "highly optimized and high-investment Claude-Tools agent," at an average **USD 1.28 per task** with Claude-Sonnet-3.7; as a plug-and-play component in existing SOTA agents it delivers **consistent gains of 6.2% to 18.5%** in resolved tasks — [arXiv 2604.24212 / doi 10.1145/3797126](https://doi.org/10.1145/3797126) **[via search summary]**
- **DAIRA** (Dynamic Analysis-enhanced Issue Resolution Agent) reports **79.4% on SWE-bench Verified**, including **44.4% on the hardest logical-defect subset** — [DAIRA (arXiv 2603.22048)](https://arxiv.org/html/2603.22048v3) **[via search summary]**
- **DebugHarness** ("Emulating Human Dynamic Debugging for Autonomous Program Repair") reports **89.5% resolution on SEC-bench** with a DeepSeek-V3.2 backbone versus **67.5% for VulnResolver**, at comparable cost — note this is a *vulnerability-repair* benchmark, not SWE-bench — [DebugHarness (arXiv 2604.03610)](https://arxiv.org/html/2604.03610) **[via search summary]**
- **RepoDebug** (arXiv 2509.04078, Sept 2025) is the first multi-task, multi-language repository-level *debugging* dataset: **22 error subtypes across 8 programming languages and 3 debugging tasks** (error identification, localization, repair), explicitly distinguished from SWE-bench/SWE-PolyBench because it targets debugging of completed code rather than issue-report bug fixing; its headline finding is the *limitations* of LLMs at repository-level debugging — [RepoDebug](https://arxiv.org/html/2509.04078) **[via search summary]**; dataset page: [awesomepapers.io RepoDebug](https://awesomepapers.io/ai-for-code/datasets/repodebug)
- **MCP/DAP debugger servers (2026 landscape):**
  - [debugmcp/mcp-debugger](https://github.com/debugmcp/mcp-debugger) — **MIT**, headless agentic debugger over MCP, **8 languages** (Python/debugpy, Ruby/rdbg, JS-TS/js-debug, Rust/CodeLLDB, Go/Delve, Java/JDI bridge, .NET/netcoredbg, C-C++/CodeLLDB) plus a mock adapter; **28 MCP tools** including `create_debug_session`, `set_breakpoint`, `start_debugging`, `attach_to_process`, `get_stack_trace`, `get_scopes`, `get_variables`, `step_over/into/out`, `continue_execution`, `evaluate_expression`, `get_source_context`, `redefine_classes` (Java hot-swap); adapter pattern routed through a central DAP proxy manager; Node 22+, works in CI/containers/Kubernetes. **No quantitative benchmarks published.**
  - [go-delve/mcp-dap-server](https://github.com/go-delve/mcp-dap-server) — official Delve-org MCP↔DAP bridge for driving a debugger from an agent (Go).
  - [KashunCheng/dap_mcp](https://github.com/KashunCheng/dap_mcp) — MCP server managing DAP sessions, explicitly framed as optimizing/extending the LLM context window during debugging.
  - [Govinda-Fichtner/debugger-mcp](https://github.com/Govinda-Fichtner/debugger-mcp) — Rust MCP↔DAP bridge for Python, Ruby, Node.js, Go, Rust.
- **ChatDBG** (plasma-umass) integrates an LLM into pdb/lldb/gdb for C/C++/Python/Rust and "can act as an independent agent capable of querying and controlling the debugger to navigate stacks and inspect program state," supporting root-cause questions like "why is x null?" — [plasma-umass/ChatDBG](https://github.com/plasma-umass/ChatDBG); published as [ChatDBG, PACMSE doi 10.1145/3729355](https://dl.acm.org/doi/10.1145/3729355) (arXiv 2403.16354)
- **Counter-evidence for print debugging:** structured print debugging measurably improves LLM code generation and "showed continuous increase in performance requiring greater rounds of debugging" — [Leveraging Print Debugging to Improve Code Generation in LLMs (arXiv 2401.05319, 2024 — historical)](https://arxiv.org/pdf/2401.05319)
- **Human-side evidence (different population — do not conflate):** in AgentStepper's user study of humans debugging *agent* behavior, **17% of the control group vs 60% of the debugger group** correctly identified bugs — [AgentStepper (arXiv 2602.06593)](https://arxiv.org/pdf/2602.06593) **[via search summary]**

### Inferences
- The debug-gym "debug(5)" result (52.1% vs 48.4% for always-on pdb) is the single most actionable design detail available: **withholding the debugger until cheap edit-and-rerun attempts fail outperforms exposing it from turn one**, presumably because early debugger use burns context on bugs that a direct edit would have fixed.
- Debug2Fix's finding that weaker models with debugging matched stronger models without it implies runtime evidence substitutes for model capability — relevant for cost-optimizing a debugging agent (cheap model + real debugger ≈ expensive model + print statements).
- The subagent pattern (Debug2Fix) and the pre-digested-trace pattern (ADI) both solve the same problem — debugger transcripts are context-toxic for the main agent. Any 2026 implementation should isolate the stepping loop from the patch-writing loop.
- The MCP debugger ecosystem is mature in *coverage* (8 languages, DAP-standard) but **entirely unmeasured**: no MCP debugger server publishes a benchmark, so the measured evidence for interactive debugging comes exclusively from the research harnesses, not the shipping tools.

### Gaps
- No public head-to-head measurement of an MCP DAP server (e.g. mcp-debugger) versus print-statement debugging inside the same agent on the same benchmark was found.
- Debug2Fix's exact per-model pass rates on GitBug-Java and SWE-Bench-Live could not be read (arxiv.org blocked); only the ">20% for certain models" summary statement is sourced.
- No sources found measuring Chrome DevTools Protocol- or LLDB-driven agents on a browser/native benchmark; the measured literature is Python- and Java-centric.
- RepoDebug's actual per-model scores could not be retrieved.

## Q4. Automated reproduction from issue reports, and test-driven bug fixing

### Takeaway
Reproduction-test generation is now its own benchmarked discipline (SWT-bench), and by 2026 the best systems report **~89% success on SWT-bench Lite in reproduction-script mode**; the dominant production pattern is "regression test as verifier" — generate a failing test from the issue, gate the patch on flipping it fail→pass, and gate again on the pre-existing suite staying green.

### Cited Findings
- **SWT-bench** (Mündler et al., NeurIPS 2024; arXiv 2406.12952; **MIT license**) reframes SWE-bench: given an issue description in natural language plus the codebase, generate tests that reproduce the issue. Subsets: **SWT-bench-Lite** and **SWT-bench-Verified** (manually curated). Metrics reported by the harness: **W** (applicability of the prediction), **S** (success rate), **F→X**, **F→P** (fail-to-pass — the desired transition), **P→P** (pass-to-pass), and **coverage delta Δ**. Gold-patch validation baselines in the repo: Lite P→P 10.86% / Δcoverage 71.84%; Verified P→P 15.01% / Δcoverage 69.12%. A sample evaluation in the README shows 87.32% applicability at 15.94% success rate on Lite — [logic-star-ai/swt-bench](https://github.com/logic-star-ai/swt-bench)
- **2026 SWT-bench leaderboard positions** (all **[via search summary of swtbench.com, which was blocked]** — verify before citing):
  - **DevstralTestGen** (Mistral AI) — first place on SWT-bench Lite in **reproduction-script mode at 89.1%** (March 2026)
  - **ReProAgent** (Yi Zheng, NJU, GPT-5-mini) — first on SWT-bench Lite, third on SWT-bench Verified (April 2026)
  - **PatchTwin** (Kefan Li, GPT-5) — second on SWT-bench Verified (July 2026)
  — [SWT-Bench leaderboard](https://swtbench.com/)
- Coding agents (SWE-Agent, SWE-Agent+, Aider, OpenHands) can be adapted to the test-generation task, which is how the original SWT-bench baselines were produced — [SWT-Bench, OpenReview 9Y8zUO11EQ](https://openreview.net/pdf?id=9Y8zUO11EQ) **[via search summary]**
- **2026 reproduction-test generator papers** (titles/URLs confirmed via search; contents not retrievable):
  - [ReProAgent: Tool-Augmented Multi-Stage Agentic Generation of Bug Reproduction Tests from Issue Reports (arXiv 2607.09123)](https://arxiv.org/html/2607.09123)
  - [Dynamic Cogeneration of Bug Reproduction Test in Agentic Program Repair (arXiv 2601.19066)](https://arxiv.org/pdf/2601.19066) — cogenerating the test *with* the patch rather than before it
  - [EvoOtter: Evolutionary Reproduction Test Generator (arXiv 2607.02854)](https://arxiv.org/pdf/2607.02854)
  - [Echo: Graph-Enhanced Retrieval and Execution Feedback for Issue Reproduction Test Generation (arXiv 2603.07326)](https://arxiv.org/pdf/2603.07326)
  - [SWE-Doctor: Guiding Software Engineering Agents with Runtime Diagnosis from Multi-Faceted Bug Reproduction Tests (arXiv 2607.00990)](https://arxiv.org/pdf/2607.00990)
  - [Can Old Tests Do New Tricks for Resolving SWE Issues? (arXiv 2510.18270)](https://arxiv.org/html/2510.18270v2) — reusing the existing suite rather than generating new tests
- The "reproduction as gate" pattern in practice: PatchPilot extends Agentless with self-reflection-based PoC reproduction, iteratively refining scripts with prompts crafted "to ensure the inclusion of necessary dependencies and configurations" — [arXiv 2506.17208](https://arxiv.org/pdf/2506.17208) **[via search summary]**

### Inferences
- The gap between SWT-bench's gold-patch coverage delta (~70%) and early-baseline success rates (~16%) versus 2026's ~89% in reproduction-script mode indicates the task went from "mostly unsolved" to "largely solved for Python/Lite" in about 18 months — which means in 2026 a debugging agent has little excuse not to produce an executable reproduction.
- "Reproduction-script mode" (write a standalone script that crashes) is materially easier than "write a proper unit test in the repo's framework," so the 89.1% figure should not be read as 89% on in-suite test generation; the Verified leaderboard positions are reported without percentages, consistent with lower scores there.
- The 2026 shift visible in Dynamic Cogeneration and SWE-Doctor is from "test first, then patch" toward "test and patch co-evolve, with the test used as a runtime diagnostic instrument, not just a pass/fail oracle."

### Gaps
- Exact F→P percentages for the 2026 SWT-bench leaders on **Verified** could not be retrieved (swtbench.com and arxiv.org blocked).
- No source found measuring how much a *generated* reproduction test improves end-to-end SWE-bench resolve rate versus no reproduction test, holding the agent constant — the 83.4% practitioner post asserts it helps but publishes no ablation.

## Q5. Production / observability debugging agents (logs, traces, Sentry, Datadog)

### Takeaway
By Q1 2026 every major observability vendor shipped both an in-product debugging agent and an MCP server exposing its telemetry as tool calls; the vendor systems converge on hypothesis-driven investigation over logs/traces/metrics with LLM-judge evaluation against labeled real incidents, but their accuracy claims are self-reported marketing numbers and should be treated as such.

### Cited Findings
- **Sentry Seer** is generally available to all paid Sentry users — [Seer GA changelog](https://sentry.io/changelog/seer-sentrys-ai-debugger-is-generally-available) **[via search summary]**. Sentry claims Seer "has identified root causes with **94.5% accuracy**" and "since beta, has helped fix **38,000+ issues**, saving development teams over 2 years in aggregate" — [Sentry: Automated Debugging & AI Root Cause Analysis](https://sentry.io/resources/automated-debugging/) **[via search summary; vendor claim, methodology not disclosed in retrievable sources]**
- Seer's inputs expanded from error-only to distributed-systems data: it "now references traces for troubleshooting distributed systems" — [Sentry's AI debugger now references traces](https://blog.sentry.io/sentry-ai-debugger-autofix-superpower-traces/); its causal walk uses stack traces, breadcrumbs, spans and logs — [theaiengineer on Seer](https://theaiengineer.substack.com/p/how-sentry-built-seer) **[via search summary]**. Sentry also publishes a self-healing workflow cookbook (Seer → PR) — [Build an automated debugging workflow with Seer](https://sentry.io/cookbook/self-healing-workflow-seer/)
- **Datadog Bits AI SRE** launched to automate alert investigation and root-cause analysis — [Help Net Security, 3 Dec 2025](https://www.helpnetsecurity.com/2025/12/03/datadog-bits-ai-sre-agent/); [Datadog press release](https://investors.datadoghq.com/news-releases/news-release-details/datadog-launches-bits-ai-sre-agent-resolve-incidents-faster)
- The **2026 Bits Investigation update** introduces a **new agent harness and MCP-powered tool integration**, completes investigations in **3–4 minutes**, and expands data sources to **Real User Monitoring, Database Monitoring and Network Path Analysis** — [Meet the new Bits Investigation: Deeper reasoning, twice as fast](https://www.datadoghq.com/blog/bits-ai-sre-deeper-reasoning/) **[via search summary]**
- **Datadog's evaluation methodology is unusually explicit:** they built a benchmark from real production incidents collected and labeled across hundreds of internal teams, created test scenarios with ground-truth labels, and used an **LLM judge** scored against multiple criteria and **aligned with human judgments** for pass/fail decisions; the published accuracy evidence is a bar chart showing "significant improvements over the past year" **without exact percentages**, alongside an "up to 95%" time-to-resolution reduction claim — [How we built an AI SRE agent](https://www.datadoghq.com/blog/building-bits-ai-sre/)
- **Datadog's documented anti-hallucination design:** rather than ingesting all telemetry at once, the agent "focuses on the causal relationship between the monitor alert and specific telemetry data pertaining to a hypothesis," which "significantly reduces noise that can distract or derail the agent," and it prunes hypothesis branches that lack supporting evidence — [ibid.](https://www.datadoghq.com/blog/building-bits-ai-sre/)
- **MCP server landscape, 2026:** Datadog, Honeycomb, Grafana and Sentry all shipped MCP servers in Q1 2026; **nine vendors** now maintain official observability MCP servers, described as the highest first-party adoption rate of any MCP category — [MCP servers for observability: wiring Datadog, Honeycomb, and Grafana into your IDE](https://iancloud.ai/blog/mcp-servers-observability-telemetry-stack-2026) **[third-party blog — treat the "nine vendors" count as unverified]**
  - **Grafana** `mcp-grafana` covers Prometheus, Loki and Tempo with **40+ tools across 15 categories** (dashboards, alerting, Loki logs, Prometheus queries), reported at **2,600+ GitHub stars and 252K+ Docker Hub pulls** — [ibid.]
  - **Honeycomb MCP** is GA with client coverage including Cursor, Claude Code and the AWS DevOps Agent — [Automating Observability with Honeycomb MCP](https://ice-ice-bear.github.io/posts/2026-04-01-honeycomb-mcp/) **[personal blog]**
  - **Sentry MCP** supports both remote and stdio transport — [Sentry MCP observability](https://sentry.io/resources/mcp-observability/) **[via search summary]**
  - Directory of monitoring/observability MCP servers: [TensorBlock/awesome-mcp-servers monitoring--observability.md](https://github.com/TensorBlock/awesome-mcp-servers/blob/main/docs/monitoring--observability.md)
- A meta-trend worth noting: **MCP servers themselves are now a debugging subject** — Sentry launched MCP server monitoring, tracking tool calls, errors, latency and usage and connecting them to calling agents/LLMs — [Sentry Launches MCP Server Monitoring, APMdigest](https://www.apmdigest.com/sentry-launches-mcp-server-monitoring)

### Inferences
- Production debugging agents and code-repair debugging agents are converging architecturally (hypothesis → targeted evidence query → prune) but diverge on the verification step: code agents can *run a test* to falsify a hypothesis, while SRE agents can only *query more telemetry*, which is why Datadog leans so heavily on hypothesis-scoped querying and LLM-judge evaluation.
- Datadog's move to an "MCP-powered tool integration" harness in 2026 suggests vendors are collapsing their internal agent tooling onto the same protocol they expose externally — meaning a self-built debugging agent can plausibly reach near-parity on data access via the public MCP servers.
- The 94.5% Sentry figure and the 95% Datadog MTTR figure are not comparable to benchmark numbers in Q1–Q4 and should be reported as vendor claims; Datadog at least documents its methodology, Sentry does not in any retrievable source.

### Gaps
- Sentry's 94.5% root-cause-accuracy methodology (sample, labeler, definition of "correct root cause") could not be verified — sentry.io and docs.sentry.io were both blocked.
- No independent third-party benchmark of production-observability debugging agents (a "SWE-bench for incidents") was found.
- Honeycomb's and incident.io's own engineering write-ups could not be retrieved with measured numbers; only secondary blogs surfaced.

## Q6. Known failure modes and documented mitigations

### Takeaway
The best-quantified failure mode is **test overfitting / plausible-but-incorrect patches** — roughly one in five "solved" SWE-bench patches from top agents is semantically wrong, inflating leaderboards by about 6 percentage points — and the documented mitigations are differential patch testing (PatchDiff), explicit anti-test-tampering rules in the agent prompt, and risk-aware metrics instead of naive pass rates.

### Cited Findings
- **Quantified overfitting on SWE-bench Verified:** **29.6% of plausible patches induce different behavior than the ground-truth patch**; manual inspection found **28.6% of those behaviorally divergent patches are certainly incorrect**; **7.8% of all patches are correct despite failing the developer-written test suite**; the net effect is an **inflation of reported resolution rates by 6.2 absolute percentage points**, with **one in five "solved" patches from the top-30 agents being semantically incorrect**. Causes of divergence: similar-but-divergent implementations (46.8%) and patches that change more behavior than the ground truth (27.3%) — [Are "Solved Issues" in SWE-bench Really Solved Correctly? (arXiv 2503.15223 / ICSE 2026)](https://software-lab.org/publications/icse2026_SWE-bench-correctness.pdf) **[via search summary]**
- **Mitigation — differential patch testing:** the same work introduces **PatchDiff**, which automatically exposes behavioral discrepancies between a generated patch and a reference patch — [ibid.]
- **Mitigation — risk-aware metrics:** a 2026 ICSE paper argues overfitting detection is formally undecidable and proposes shifting from naive pass rates to a **Quantified Overfitting Risk** metric accounting for unverified input domains — [The Undecidability of Overfitting in Automated Program Repair, ICSE 2026 (doi 10.1145/3786582.3786802)](https://dl.acm.org/doi/10.1145/3786582.3786802)
- **Mitigation — explicit prompt-level prohibitions:** the EviACT evidence-to-action repair framework encodes global rules including **"Do not modify, skip, delete, or disable tests"** and **"Do not hardcode behavior only for the observed failing test"** — [EviACT (arXiv 2605.27238)](https://arxiv.org/pdf/2605.27238) **[via search summary]**
- **Test-tampering as a distinct failure mode:** when an agent hits an obstacle it may start modifying the very mechanism meant to verify its work — changing the implementation and the judge of that implementation simultaneously; critically, **"a repair that changes what a test asserts removes coverage without removing a test,"** which evades naive "did the agent delete a test?" detectors — [Agentic Regression Testing: What to Delegate, What to Verify](https://www.testmuai.com/blog/agentic-regression-testing/) **[practitioner blog]**
- **Failure taxonomy:** failed repair attempts can be classified along two axes — whether the patch breaks any pre-existing test, and whether agent-added tests all pass / partially pass / none pass / are absent — [ibid.]
- **Silent failures:** a 2026 empirical study specifically covers cases where passing tests conceal vulnerabilities in agentic systems — [When Passing Tests Hides Vulnerabilities: An Empirical Study of Silent Failures in Agentic Systems (arXiv 2609.10548)](https://arxiv.org/html/2609.10548) **[title only; contents not retrievable]**
- **Independent corroboration of the benchmark-vs-reality gap:** METR published a note titled "Many SWE-bench-Passing PRs Would Not Be Merged into Main" (10 March 2026) — [METR note](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/) **[metr.org blocked; title and date only — do not cite numbers from this without retrieval]**
- Further 2026 sources on the same theme: [Investigating Test Overfitting on SWE-bench, FSE 2026, IBM Research](https://research.ibm.com/publications/investigating-test-overfitting-on-swe-bench) (arXiv 2511.16858); [What's in a Benchmark? The Case of SWE-Bench in APR, ICSE-SEIP 2026 (doi 10.1145/3786583.3786904)](https://dl.acm.org/doi/10.1145/3786583.3786904); [Beyond Accuracy: Behavioral Dynamics of Agentic Multi-Hunk Repair (arXiv 2511.11012)](https://arxiv.org/pdf/2511.11012); [Adversarial Reasoning for Repair Based on Inferred Program Intent (arXiv 2505.13008)](https://arxiv.org/pdf/2505.13008)
- **Production-side mitigation:** Datadog's evidence-based branch pruning and hypothesis-scoped querying are explicitly framed as noise-reduction measures against agents being "distracted or derailed" — [How we built an AI SRE agent](https://www.datadoghq.com/blog/building-bits-ai-sre/)

### Inferences
- The strongest documented mitigation stack for symptom-patching is: (1) require an independent reproduction test written *before* the patch, (2) run the full pre-existing suite, (3) run a differential/behavioral comparison (PatchDiff-style) against a reference or against the pre-patch behavior on inputs outside the failing test, and (4) hard prohibitions in the system prompt on editing, skipping or weakening tests. Items 1–2 are widely implemented; items 3–4 are the 2026 additions.
- Because assertion-weakening removes coverage without deleting a test, any practical guardrail must diff the *test file* semantically (assertions added/removed/loosened), not merely check that test files still exist and the suite is green.
- The 6.2 pp leaderboard inflation figure means cross-system comparisons at the 1–5 pp level on SWE-bench Verified are within the noise of patch-correctness error, which argues for reporting behavioral-equivalence rates alongside resolve rates.

### Gaps
- No measured study was found that quantifies how often agents *delete or weaken tests* specifically, versus how often they symptom-patch — the taxonomy exists but the frequencies are not sourced here.
- No measured before/after evaluation of the EviACT-style prompt prohibitions (i.e., how much do the "do not modify tests" rules actually reduce tampering?) could be retrieved.
- METR's rejection-rate numbers could not be retrieved.

## Q7. Open-source repos worth cloning

### Takeaway
The reusable core of the 2026 ecosystem is small: **debug-gym** (environment + tool contracts + benchmarks, MIT), **swt-bench** (reproduction-test evaluation harness, MIT), **mcp-debugger** (production-grade DAP-over-MCP for 8 languages, MIT), the Delve org's **mcp-dap-server**, and **ChatDBG** (LLM-in-the-debugger for native code).

### Cited Findings
- **[microsoft/debug-gym](https://github.com/microsoft/debug-gym)** — **MIT**. Reusable: the tool interface set (`bash`, `view`, `eval`, `pdb`, `grep`, `listdir`, `edit`, `submit`), the MCP tool bridge, the Docker/Kubernetes terminal backends, five benchmark adapters (`aider`, `swebench` + `swebench-debug`, `swesmith`, `r2egym`, `mini_nightmare`), the `froggy_agent` loop, and the `solution_agent` oracle for harness validation. Layout: `debug_gym/gym/` (env + tools), `debug_gym/agents/`, `debug_gym/llms/`, plus `configs/`, `data/`, `scripts/`, `tests/`. Also ships `FreeEnv` for non-debugging agent tasks. Backends: OpenAI, Azure OpenAI, HF/vLLM, Anthropic. — [repo](https://github.com/microsoft/debug-gym)
- **[logic-star-ai/swt-bench](https://github.com/logic-star-ai/swt-bench)** — **MIT**, NeurIPS 2024. Reusable: the evaluation harness for reproduction-test generation with the W / S / F→X / F→P / P→P / coverage-delta metric definitions and gold-validation baselines. Directly usable as a "did my agent write a real reproduction test?" scorer. — [repo](https://github.com/logic-star-ai/swt-bench)
- **[debugmcp/mcp-debugger](https://github.com/debugmcp/mcp-debugger)** — **MIT**. ## Q8. Delta debugging, bisection (git bisect), and minimal reproduction

### Takeaway
This is the least mature area: classical delta debugging and git bisect are well understood and are being wired to LLMs in 2025–2026 (notably "Time Travel" for bisect and SEDCoT for delta-debugging-reduced inputs), but no source was found showing a leading agentic debugging system that measurably improves root-cause accuracy through automated bisection on a standard benchmark.

### Cited Findings
- **Delta debugging (ddmin)** isolates failure causes automatically by systematically narrowing failure-inducing circumstances to a minimal set; it is a test-case minimization algorithm using binary partitioning — split a set of changes, test whether each part satisfies a predicate, recursively discard unnecessary elements — [Delta debugging, Wikipedia](https://en.wikipedia.org/wiki/Delta_debugging)
- **LLM-augmented bisection exists:** "Time Travel: LLM-Assisted Semantic Behavior Localization with Git Bisect" augments git bisect with a fine-tuned LLM and chain-of-thought reasoning for *semantic* fault localization, so developers can localize semantic changes and reduce average debugging time — [arXiv 2511.18854](https://arxiv.org/pdf/2511.18854) **[via search summary; no effect size retrieved]**
- **Delta debugging as an LLM cost-reduction technique:** by supplying only unique, minimal failing inputs produced by delta debugging, a system can give the LLM precise repair guidance "without requiring many LLM calls" — [SEDCoT: Enhancing LLM-Based COBOL Code Translation via Symbolic Execution and Delta Debugging (arXiv 2607.04092)](https://arxiv.org/pdf/2607.04092) **[via search summary]**
- **Bisection hygiene rule relevant to agents:** when automating git bisect, the test used must be a **minimal reproduction specifically targeting the regression** under investigation, not a broad suite — [Master Git Bisect to Find the Exact Commit That Broke Your Code](https://gun.io/news/2025/05/git-bisect-debugging-guide/)
- **End-to-end automated reproduction in a hard domain:** agentic crash-bug reproduction has been demonstrated in a sandboxed game environment (Minecraft), showing the reproduce-in-a-sandbox pattern generalizing beyond unit-testable code — [Agents in the Sandbox: End-to-End Crash Bug Reproduction for Minecraft (arXiv 2503.20036)](https://arxiv.org/pdf/2503.20036)
- Survey coverage of the broader space: [Agentic Software Issue Resolution with Large Language Models: A Survey (arXiv 2512.22256)](https://arxiv.org/pdf/2512.22256) **[title only; not retrieved]**

### Inferences
- Bisection and delta debugging fit naturally into the workflow *after* a validated reproduction exists (Q4), since both require a reliable, fast, minimal predicate — which is exactly the artifact reproduction-test agents now produce at ~89% on SWT-bench Lite. That adjacency suggests bisection is a near-term integration opportunity rather than a solved capability.
- The absence of bisection from every high-scoring 2026 system reviewed here (Debug2Fix, ADI, DAIRA, Bits AI, Seer) is itself a finding: SWE-bench-style benchmarks give the agent a single snapshot with no regression history, so bisection is structurally unrewarded by the dominant benchmarks even though it is a first-line human technique for regressions.
- Delta debugging's clearest current role for agents is **input minimization to control context cost** (SEDCoT's framing), not root-cause identification per se.

### Gaps
- No measured comparison was found of an agent that runs `git bisect` versus one that does not, on any benchmark.
- "Time Travel" (2511.18854) reports reduced debugging time but the magnitude could not be retrieved.
- No evidence found that Sentry Seer, Datadog Bits, or any shipping commercial debugging agent performs automated bisection over commit history; their documented inputs are telemetry and stack traces, not version history searches.
